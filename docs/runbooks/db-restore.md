# Runbook: Restoring the PostgreSQL database

This runbook covers how to restore the `lev_trak_har` production database: the Azure Database for
PostgreSQL Flexible Server `psql-leave-trac-har` in resource group `leave-trac-har` (UK South),
defined in `infra/main.tf`.

## 1. Backup configuration (source of truth: `infra/main.tf`)

| Setting | Value | Where |
| --- | --- | --- |
| Automated backups | Enabled (on by default for Flexible Server) | `azurerm_postgresql_flexible_server.postgresql` |
| Retention | 35 days (`backup_retention_days = 35`) | `infra/main.tf` |
| Off-region copy | Geo-redundant backups (`geo_redundant_backup_enabled = true`), copied to the Azure paired region (UK West) | `infra/main.tf` |
| Point-in-time recovery | Supported: you can restore to any second in the retention window | Azure platform feature |
| Network | Public access disabled; you reach the server through private endpoint `pe-psql-leave-trac-har` | `infra/main.tf` |

Do not lower `backup_retention_days` below 30 or turn off `geo_redundant_backup_enabled`. The
`rel.backup_configured` requirement depends on both settings. Note that you can only enable geo-redundancy
when the server is created. If you change that setting, Terraform will recreate the server.

## 2. When to use this runbook

- **Point-in-time restore (PITR):** use this for data corruption, a bad migration, or accidental deletes.
  You restore into the same region (UK South) at a timestamp just before the incident.
- **Geo-restore:** use this when the UK South region or the primary server is unavailable. You restore
  from the geo-redundant backup into UK West.

A restore always creates a **new** server. Azure never overwrites the source server. After the
restore you move the application over to the new server.

## 3. Prerequisites

- Azure CLI 2.50+ (`az login`), with `Contributor` on resource group `leave-trac-har` and on the hub
  resource group that holds the private DNS zone `privatelink.postgres.database.azure.com`
  (`var.hub_resource_group`).
- Access to the VNet/subnet used by the app (`var.vnet_id`, `var.subnet_id`), so `psql` can reach the
  private endpoint.
- The PostgreSQL admin credentials (`psqladmin`, plus the password generated by
  `random_password.postgresql_admin`). The restored server keeps the source server's admin login and
  password.
- The application's database settings, which `backend/config/settings/base.py` reads:
  `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`.

## 4. Procedure

### 4.1 Declare the incident and pick a restore point

1. Record the incident start time in UTC. For PITR, pick a restore time a little **before** the
   corrupting event.
2. Check that the restore point is inside the window:
   ```bash
   az postgres flexible-server show -g leave-trac-har -n psql-leave-trac-har \
     --query "{earliestRestore: backup.earliestRestoreDate, retentionDays: backup.backupRetentionDays, geo: backup.geoRedundantBackup}"
   ```
3. If you can, stop writes so no new data is lost during cutover: scale the backend down or put it into
   maintenance.

### 4.2a Point-in-time restore (same region)

```bash
RESTORE_TIME="2026-01-01T12:00:00Z"            # UTC, ISO-8601
TARGET="psql-leave-trac-har-restore-$(date -u +%Y%m%d%H%M)"

az postgres flexible-server restore \
  --resource-group leave-trac-har \
  --name "$TARGET" \
  --source-server psql-leave-trac-har \
  --restore-time "$RESTORE_TIME"
```

### 4.2b Geo-restore (region outage)

```bash
TARGET="psql-leave-trac-har-geo-$(date -u +%Y%m%d%H%M)"

az postgres flexible-server geo-restore \
  --resource-group leave-trac-har \
  --name "$TARGET" \
  --source-server psql-leave-trac-har \
  --location ukwest
```

Geo-restore uses the latest geo-replicated backup. Expect an RPO of up to about 1 hour.

### 4.3 Reconnect private networking

Public network access is disabled, so the new server needs its own private endpoint. That endpoint must
be registered in the shared private DNS zone:

```bash
SERVER_ID=$(az postgres flexible-server show -g leave-trac-har -n "$TARGET" --query id -o tsv)

az network private-endpoint create \
  --resource-group leave-trac-har \
  --name "pe-$TARGET" \
  --subnet "<app subnet resource ID (var.subnet_id)>" \
  --private-connection-resource-id "$SERVER_ID" \
  --group-id postgresqlServer \
  --connection-name psql-privateserviceconnection

az network private-endpoint dns-zone-group create \
  --resource-group leave-trac-har \
  --endpoint-name "pe-$TARGET" \
  --name psql-dns-zone-group \
  --private-dns-zone "<resource ID of privatelink.postgres.database.azure.com in var.hub_resource_group>" \
  --zone-name postgres
```

For a geo-restore into UK West, the subnet must be in a VNet in UK West. That VNet must also be linked
to the private DNS zone.

### 4.4 Verify the restored data

From a host inside the VNet:

```bash
psql "host=$TARGET.postgres.database.azure.com port=5432 dbname=<POSTGRES_DB> user=psqladmin sslmode=require"
```

Checks:
- `\dt` shows the Django tables (`accounts_user`, `leave_*`, `attendance_*`, `django_migrations`).
- `SELECT max(applied) FROM django_migrations;` matches the release you expect.
- Row counts and the newest timestamps in the key tables (users, leave requests, attendance) look
  plausible for the restore point.
- From a backend container pointed at the new host, `python manage.py migrate --check` and
  `python manage.py check --deploy` pass.

### 4.5 Cut the application over

1. Set `POSTGRES_HOST` to `<TARGET>.postgres.database.azure.com` in the backend's runtime
   configuration. Leave the other `POSTGRES_*` values as they are unless they differ.
2. Restart or redeploy the backend, then smoke-test login and the leave and attendance endpoints.
3. Turn writes back on and close the maintenance window.

### 4.6 Reconcile Terraform

Terraform does not know about the restored server, and `infra/main.tf` still names
`psql-leave-trac-har`. Pick one of these:
- **Keep the restored server:** rename the resource in `infra/main.tf` (or import it using
  `terraform import azurerm_postgresql_flexible_server.postgresql <SERVER_ID>`, plus the new private
  endpoint), then run `terraform plan`. Confirm that `backup_retention_days = 35` and
  `geo_redundant_backup_enabled = true` show no drift.
- **Restore back to the original name:** after the incident, delete the old server, run a PITR from the
  restored server to `psql-leave-trac-har`, then repeat steps 4.3–4.5.

Keep the old server, stopped, until the post-incident review is complete. Then delete it.

## 5. Targets

| Metric | Target |
| --- | --- |
| RPO (PITR) | ≤ 5 minutes (WAL-based) |
| RPO (geo-restore) | ≤ 1 hour |
| RTO | ≤ 4 hours, including verification and cutover |

## 6. Restore test record

You must run a full restore test (steps 4.1–4.4, against a non-production target name) **before
go-live**. After go-live, repeat it at least every 6 months and after any change to the database
infrastructure. Each test must be recorded below. Do not mark the requirement as met until there is at
least one row with outcome **Pass**.

| Date (UTC) | Type (PITR / geo) | Restore point | Target server | Time to restore | Verified by | Outcome | Notes |
| --- | --- | --- | --- | --- | --- | --- | --- |
| _Not yet performed_ | | | | | | | Pre-go-live test outstanding |

After a test, delete the test server and its private endpoint so they don't keep incurring cost:

```bash
az network private-endpoint delete -g leave-trac-har -n "pe-$TARGET"
az postgres flexible-server delete -g leave-trac-har -n "$TARGET" --yes
```
